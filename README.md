# 30 до 30

Telegram Mini App — трекер 30 заданий до тридцатилетия. 4 уровня, 100 баллов, сундук с
наградой в финале.

## Что уже готово (этапы 1–3, UI на моках)

- Каркас приложения под iPhone 16 Pro: safe-area, `--tg-viewport-stable-height`, нижний
  таб-бар из 5 вкладок.
- Все 30 задач с описаниями, подсказками «что снять» и критериями проверки для AI
  (`shared/tasks.ts`).
- Логика разблокировки: уровень 1 — по одной задаче, уровень 2 — окно из трёх,
  уровни 3–4 — по одной; сундук при 100 баллах (`shared/progress.ts`).
- Прогресс-бары уровня и общий, карточки со всеми состояниями (закрыта / доступна /
  выполнена), орнаментальные разделители и главы.
- Шторка задания с описанием, подсказкой по фото и демо-проверкой «AI» (пока
  имитация, без сервера).
- Сундук: закрытый, готовый, анимация открытия с частицами; после открытия приз
  вылетает из сундука и заменяет его, таймер исчезает при 100 баллах.
- Ручное подтверждение задания по 6-значному коду — на случай, когда фото нет или
  проверка его не приняла.
- Обратный отсчёт до 10 января 2027, 00:00 МСК.
- Панель разработчика для проверки анимаций и переходов без фото.

## Запуск

```bash
npm install
npm run dev        # http://localhost:5173
npm run build      # проверить сборку
```

### Если экран пустой

- Открывать нужно `http://localhost:5173` (после `npm run dev`) или
  `http://localhost:4173` (после `npm run preview`), а **не** файл `dist/index.html`
  двойным кликом — из `file://` ES-модули не загружаются.
- Внешние `telegram.org` и Google Fonts больше не блокируют отрисовку: скрипт Telegram
  грузится асинхронно, шрифты — через `media="print"`.
- Если приложение всё же падает, теперь показывается экран с текстом ошибки, а не белая
  страница. Тот же текст дублируется в консоли браузера.

## Режим разработчика

Нужен, чтобы проходить задания без фото и смотреть все анимации:

- долгое нажатие (3 с) на логотип «30 ДО 30» в шапке, или
- открыть приложение с `?dev=1`.

Появляется кнопка **DEV**. Чтобы выйти из режима, нажми в панели
**«Выйти из режима разработчика»** — вернутся обычные правила и закрытый сундук.

В панели:

- завершить следующую доступную задачу;
- открыть сундук без 100 баллов — репетиция анимации, результат не сохраняется;
- отметить все 30 и открыть сундук;
- переключить следующую проверку фото на «провал»;
- сбросить прогресс;
- показать подсказку об аллее славы при закрытии панели (одноразовый чекбокс);
- вручную отметить/снять любую задачу;
- открыть карточку задания жены и прочитать её апелляцию: пояснение, замечания
  до пересмотра и ответ ИИ.

В продакшене панель будет доступна только Telegram ID владельца.

## Аллея славы

Счётчик баллов в шапке — это кнопка. Она открывает аллею славы: горизонтальную
витрину всех 30 заданий.

- Выполненные карточки показывают фото, похвалу ИИ и дату; невыполненные — серый
  знак вопроса и название задания.
- Карточки скроллятся по кругу с эффектом полуокружности: по центру одна,
  по краям выглядывают соседние. После последней снова идёт первая.
- После отпускания карточка доводится до центра сама — и на телефоне, и на
  десктопе, — даже если быстрый флинг остановился между двумя карточками.
- При открытии показывается первая карточка первого уровня.
- Нажатие на карточку возвращает к списку заданий нужного уровня, прокручивает
  страницу к этому заданию и подсвечивает его.

При первом запуске поверх интерфейса появляется затемнение, счётчик остаётся ярким,
а рядом показывается пальчик. Факт показа хранится вместе с прогрессом в
`localStorage` (`thirty-progress-v1`).

Чтобы посмотреть подсказку ещё раз, в dev-панели отметь чекбокс «Показать подсказку
об аллее после закрытия панели» — обучение запустится, как только закроешь панель, и
чекбокс обнулится сам. Сброс прогресса подсказку не включает и панель не закрывает.

Фото выполненных заданий один раз догружаются в фоне после запуска
(`src/api/photoCache.ts`, по два запроса за раз) и остаются в памяти до закрытия
приложения. Аллея и шторка задания берут их из одного общего кэша: повторное
открытие ничего не запрашивает, прокрутка по кругу — тоже. После новой загрузки
фото или апелляции кэш этого задания сбрасывается, и следующее открытие подтянет
свежие данные.

В dev-режиме аллея показывает карточки жены. Их не предзагружаем: фото подтягиваются
по одному через `/api/dev/wife-task`, только когда карточка подъезжает к экрану, с
запасом 2–3 карточки по горизонтали. Все 30 base64-кадров разом не тянутся, а три
копии карточки делят один запрос.

## Ручное подтверждение

Если фото нет или AI его не принял, задание можно засчитать вручную:

1. Открой доступную задачу и нажми «🔑 Засчитать вручную».
2. Попроси мужа ввести код из 6 цифр.

Код по умолчанию — **300036**. Чтобы поменять, создай в корне проекта файл
`.env.local`:

```
VITE_MANUAL_PIN=123456
```

Сейчас код проверяется в браузере (для личного приложения это нормально). На этапе
сервера проверка переедет в Cloudflare Worker и перестанет попадать в бандл.

## Как AI оценивает фото

У каждой задачи в `shared/tasks*.ts` есть два списка:

- **required** — обязательные пункты, которые должны быть видны на фото. У каждого
  есть `id`, описание `label`, формулировка нехватки `miss` и максимальный вес `weight`;
- **optional** — необязательные детали. Они только хвалятся и никогда не снижают балл.

Оценка считается от 100 вниз, а не по таблице уровней:

- все обязательные пункты видны → 100;
- за каждый отсутствующий или нечитаемый пункт вычитается вес × `severity`
  (0.05–1), то есть не больше полного веса пункта;
- 70 и выше — задание засчитано, ниже 70 — нет;
- скриншот, чужое фото, монтаж, чёрный или нечитаемый кадр, посторонняя сцена
  (кроме заданий, где скриншот нужен по смыслу) — 0 баллов и провал;
- если не видно ни одного обязательного пункта, оценка тоже 0 — без «утешительных»
  процентов за то, что сумма весов меньше 100.

Модель не придумывает критерии: она возвращает `id` пункта, `state` (`missing` или
`partial`) и `severity` — насколько сильно пункта не хватает. Подпись и вес берутся
из рубрики, а штраф равен весу × severity, поэтому выше веса модель не поднимется.
За счёт дробной severity оценки получаются живыми: не только −15 и −35, но и −7,
−24, −31. Ориентиры для модели: 0.9–1 — пункта почти нет, 0.6–0.85 — заметно не
хватает, 0.3–0.55 — видна часть, 0.05–0.25 — мелкая деталь.

### Оригинальность кадра

Смысл квеста — снять самому, поэтому скачанная из интернета картинка не должна
приносить баллы. Проверка идёт четырьмя слоями, от самого надёжного к мягкому.

1. **Повтор кадра.** Браузер считает dHash — отпечаток 8×8 по яркости соседних
   точек, 16 hex-знаков. Сервер хранит его в `photos.fingerprint` и сравнивает с
   прошлыми загрузками по расстоянию Хэмминга: до 6 различий из 64 — тот же
   снимок. Совпадение с фотографией за другое задание или у другого участника —
   0 баллов. Своё же задание можно перезагрузить тем же файлом: это повторная
   попытка, а не плагиат.
2. **Форма кадра.** Полноэкранный скриншот телефона после сжатия до 1280 px
   имеет пропорции около 590×1280. Камера так не снимает: 4:3, 3:4, 16:9.
   Кадр с соотношением сторон от 2.02 и выше (или от 0.495 и ниже) получает 0 —
   кроме задания «Ролик 1 секунда в день» (`allowScreenshot`) и заданий с
   коллажем или сеткой (`allowCollage`).
3. **Взгляд модели.** В ответе появилось поле `source`: `own`, `suspicious` или
   `downloaded`. Значение `downloaded` ставится только при прямой улике — водяной знак
   фотостока, подпись сайта, рамка и поля как у картинки из Pinterest, текст
   поверх кадра, интерфейс галереи или соцсети; улика называется в
   `source_note`. Такой кадр — 0 баллов. `suspicious` — стоковая постановка без
   прямых улик: −20, чтобы скачанная картинка не получала 100, но честный кадр
   всё равно проходил.
4. **Отдельный проход про происхождение.** После того как фото прошло по
   содержанию, сервер задаёт модели ещё один узкий вопрос — только про
   происхождение кадра, с конкретными признаками каталога, витрины и стока.
   Ответы основного прохода и этого объединяются: побеждает более тяжёлое
   подозрение. Вызов идёт только для фото, которые иначе проходят, поэтому явные
   провалы за него не платят.

В подсказку этому проходу передаются метаданные исходного файла: снято ли на
камеру, модель, программа обработки и дата съёмки. Браузер читает их из JPEG до
пережатия — после canvas они теряются. Отсутствие данных камеры само по себе не
приговор (мессенджеры вырезают метаданные), но вместе с каталожной картинкой это
веский довод.

Ответы модели, которые попадают в интерфейс, проверяются на русский язык: если
модель ответила по-английски, вместо её текста показывается понятная русская
фраза.

Задания, где кадр собирается в редакторе, отмечены флагом `allowCollage`: `l1-2`,
`l1-4`, `l2-1`, `l2-4`, `l2-6`, `l2-11`, `l3-5`, `l3-7`. Для них рамки, поля и
стыки между фрагментами не считаются признаком скачанной картинки, отсутствие
метаданных камеры ожидаемо, а проверка формы кадра не применяется. У «Карты
желаний» (`l2-6`) отдельная оговорка `formatHint`: картинки внутри — вырезки из
журналов и распечатки из интернета, так и задумано. Второй ракурс для коллажей не
предлагается — сравнивать нечего; если сомнение ошибочно, остаётся апелляция.

Если модель поставила `suspicious`, минус помечается как сомнение в
оригинальности. В шторке задания он выделен отдельным блоком: кнопка «Доказать,
что фото моё» открывает загрузку второго кадра. Основное фото остаётся в профиле и
в аллее — второй снимок ничего не заменяет. Сервер отправляет оба кадра модели и
проверяет три вещи: та же ли это сцена (`same_scene`), снята ли она с другой точки
(`fresh_angle`) и не является ли второй кадр копией первого (`same_image`).
Дополнительно сравниваются отпечатки: если второй кадр — тот же файл или кроп,
попытка не тратится, сразу приходит просьба снять с другой точки. Если сцена та же
и ракурс новый, минус снимается и баллы возвращаются; иначе он остаётся, а
объяснение ИИ сохраняется. Попытка одна на фото, как и у апелляции.

Сомнение в оригинальности снижает баллы, но не проваливает кадр, который прошёл по
содержанию: иначе честное фото снималось бы на 70% из-за подозрения и не
сохранялось, а доказать было бы уже нечего.

Полностью заменить обратный поиск по картинке это не может: если фото из
интернета без водяного знака и не повторяет уже загруженное, отличить его от
личного снимка по одному кадру невозможно. Но совпадающие и явно чужие кадры
отсекаются, а прямых 100 баллов за скачанное больше не будет.

Перед сохранением оценки сервер делает второй проход: просит модель перепроверить
только заявленные минусы и снимает те, где предмет на самом деле есть. Это защищает
от ложных «не хватает», из-за которых хорошее фото раньше проваливалось. Второй
проход запускается только если минусы есть, поэтому обычная проверка не удлиняется.

В интерфейсе похвала и список минусов разделены: проценты выводятся жёлтым
(`−15%`), рядом — понятная причина («меньше трёх образцов»). Это же хранится
в D1 в колонке `photos.deductions` как JSON.

Минусы видны и при провале: если фото не засчитано, под заголовком «Что
не засчитали» показывается тот же список с раскрытием требования — иначе по
одной похвале невозможно понять, что исправить в следующем кадре.

У каждого минуса можно раскрыть подробности: полное требование рубрики («что
должно быть видно»), что именно не засчитали и максимальный вес пункта. Это нужно,
чтобы апелляцию можно было писать по конкретному критерию, а не наугад.

Правило для рубрик: каждый обязательный пункт должен быть выводим из описания
задания или подсказки «что снять». Требование, которое нельзя ни предусмотреть по
тексту, ни проверить по кадру (как «свеча в интерьере» на крупном плане), не может
снижать балл. Такие пункты убраны или перенесены в необязательные — см. ниже.

В dev-панели в карточке задания жены у каждого минуса есть `×` — если ИИ всё-таки
ошибся, минус можно убрать вручную, и оценка пересчитается.

### Что поправлено в рубриках

- «Свеча ручной работы» — убран обязательный «интерьер» на крупном плане, где его
  нельзя проверить; место свечи теперь необязательная похвала.
- «Холст в четыре руки» — «следы ребёнка» требовали доказать, что мазки оставил
  именно ребёнок. Теперь пункт засчитывается и по хаотичным мазкам, и по ребёнку с
  красками у работы: совместное творчество видно, даже если авторство каждого мазка
  не установить.
- «Монетка с мостика» — зимний пейзаж был обязательным на 15%, хотя в подсказке
  значился как «приветствуется»; перенесён в необязательные.
- «Слепой поворот» — убран обязательный сезон (его не было ни в описании, ни в
  подсказке), а «место новое» заменено на проверяемое «кадр снят на улице, а не из
  окна».
- «Шавасана в наушниках» — «видно, что это дома» нельзя доказать по затемнённой
  комнате; пункт стал необязательным.
- «Дуэль у Чижика» — зимний Петербург был обязательным на 15% без упоминания в
  тексте; теперь это бонус.
- «Кофейное бинго» — рубрика требовала три напитка и три кадра, хотя подсказка
  прямо разрешает два места; порог приведён к двум.
- «Альпаки» и «Загородный отель» — подсказки к фото дополнены так, чтобы человек на
  месте понимал про человека в кадре и про приметы отеля.

### Апелляция

Оспорить снижение баллов можно прямо в шторке задания, у принятого фото: кнопка
«Оспорить снижение баллов» открывает поле на 500 символов со счётчиком — этого
хватает на 1–3 предложения. Апелляция общая: за один раз пересматриваются все минусы
фото, а не по одному.

Модель получает фото, описание задания, текущие минусы и пояснение человека. По
**каждому** пункту она обязана вернуть число `reduce` — сколько процентных пунктов
вернуть (0, если замечание подтверждается). Пункты оцениваются независимо: по одному
можно вернуть часть или всё, по другому — ничего. Промпт задаёт шкалу: четверть или
треть штрафа — довод правдоподобен лишь отчасти, половина — убедителен наполовину,
две трети — остаётся мелкая деталь, полный штраф — замечание снимается. Крайние
значения разрешены только при очевидном решении, чтобы апелляция не выглядела
бинарной «всё или 1%». Сервер зажимает число в диапазон от 0 до текущего штрафа,
поэтому добавить новые минусы или увеличить штраф модель не может — оценка только
растёт.
Даже если ИИ не согласен, каждый оставшийся минус уменьшается хотя бы на 1% — не
только самый крупный. Единственная попытка не должна сгорать впустую, и в ответе ИИ
об этом не упоминается.

Если первый проход отказал по каким-то пунктам, сервер делает узкую перепроверку
только этих пунктов: «подтверждает ли кадр довод человека — полностью, частично или
нет». Она не добавляет новых замечаний, но не даёт честному пояснению утонуть в
одном проценте: при подтверждении пункт снимается целиком, при частичном — наполовину.
Если перепроверка не ответила, остаётся результат первого прохода.

Похвала от апелляции не меняется: результат пересмотра хранится отдельно и не
затирает исходный текст о том, что получилось. В карточке остаётся отметка
«Результат пересмотрен: было → стало», а по кнопке «Посмотреть апелляцию» можно
открыть исходные минусы, своё пояснение и ответ ИИ.

Ответ ИИ на апелляцию развёрнутый: 3–6 предложений, по каждому оспоренному пункту —
что именно видно на снимке, почему довод не меняет решение и какая деталь или ракурс
нужны, чтобы замечание сняли. Общие «спасибо за пояснение, но не могу» промпт
запрещает, а выдумывать требования вне списка замечаний — тоже.

Подать апелляцию можно один раз на одно загруженное фото. Если новое фото окажется
лучше и сохранится, это будет новая запись и новая возможность. Так нельзя пятью
апелляциями отменить один и тот же минус.

Повторная загрузка: уже засчитанное задание можно улучшить — в шторке есть кнопка
«Загрузить новое фото». Модель получает прошлую оценку и список минусов, проверяет,
исправлены ли замечания, и новый кадр сохраняется только если стал строго лучше.
Баллы при этом не начисляются повторно.

В dev-панели есть кнопка «Переоценить фото жены (N)». Сначала открывается список
заданий с чекбоксами: у каждого видно, сколько баллов сейчас и была ли апелляция,
задания без сохранённого фото недоступны. Изначально ничего не отмечено — выбираешь
по одному. Верхний чекбокс «Выбрать все» отмечает всё разом, повторное нажатие снимает
все отметки; при частичном выборе он показывается прочёркнутым. Подтверждаешь — и
пересчитываются только выбранные. Для каждого задания показывается отчёт
«было → стало · причина».

Если Workers AI отвечает `ai_unavailable`, запрос повторяется автоматически: три
попытки с паузами, чтобы у задания всё-таки появился результат. Ошибка в отчёте
остаётся только после исчерпания попыток.

Если фото уже оспаривалось и переоценка сделала его хуже, отметка об апелляции
снимается: попытку можно использовать заново на новых минусах. Если оценка осталась
прежней или выросла, апелляция остаётся использованной.

Перед деплоем этой версии примените миграции:

```bash
npx wrangler d1 execute thirty-db --remote \
  --file=./migrations/2026-11-11-photo-deductions.sql
npx wrangler d1 execute thirty-db --remote \
  --file=./migrations/2026-11-11-photo-appeal.sql
npx wrangler d1 execute thirty-db --remote \
  --file=./migrations/2026-11-12-appeal-details.sql
npx wrangler d1 execute thirty-db --remote \
  --file=./migrations/2026-11-13-photo-originality.sql
npx wrangler d1 execute thirty-db --remote \
  --file=./migrations/2026-11-13-photo-proof.sql
```

Первая миграция добавляет `photos.deductions`, вторая — поля апелляции, третья —
снимок минусов и ответ ИИ на момент пересмотра, четвёртая — `photos.fingerprint`
для поиска повторных кадров, пятая — поля доказательства оригинальности. Если
первая–третья уже применены, повторять их не нужно: достаточно четвёртой и пятой.

## Файл приза

QR-сертификат — чувствительные данные, поэтому в `public/` его класть нельзя: всё
содержимое `public/` доступно любому по прямой ссылке.

Приз хранится в таблице `prizes` базы D1 и выдаётся только через `GET /api/prize`:

- запрос должен содержать валидный Telegram `initData`;
- Telegram ID должен быть в allowlist (`OWNER_TELEGRAM_ID` / `USER_TELEGRAM_ID`);
- сундук должен быть открыт (`app_state.chest_opened = 1`).

Загрузка приза: открыть режим разработчика (удержание логотипа более 3 секунд) под
Telegram ID владельца → «Загрузить QR-приз». Подходят PNG, JPEG и WebP размером
примерно до 1 МБ. Там же кнопка «Показать QR-приз»: владелец может увидеть и проверить
приз заранее, не дожидаясь открытия сундука.

Файл `public/assets/prize-qr.png` используется только как локальная заглушка вне
Telegram. Настоящий QR туда не кладём.

Если внутри QR зашита `http(s)`-ссылка, приложение распознаёт её локально на устройстве
и показывает кнопку «Открыть сертификат». Ссылка не выводится текстом и не передаётся
на сервер: в D1 хранится только сама картинка.

## Принятые решения

| Вопрос | Решение |
|---|---|
| База данных | Cloudflare D1 (бесплатно, без карты, всё в одном аккаунте с API и AI) |
| Пользователи | Один человек + режим разработчика для владельца |
| Фото | Хранить только одобренные (отклонённые не сохраняются) |
| AI | Cloudflare Workers AI как основной; Gemini — проверить как fallback |
| Хостинг | Cloudflare Pages + Pages Functions, код и CI на GitHub |
| Дедлайн | 10 января 2027, 00:00 МСК |
| Тема | Только тёмная, фэнтези в духе Clash Royale, без ассетов Supercell |
